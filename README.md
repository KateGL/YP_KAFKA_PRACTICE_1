# Kafka Demo: Producer + 2 Consumers (Single & Batch)

Проект демонстрирует работу с Apache Kafka на Python с использованием библиотеки `confluent-kafka`:
- **Producer**: асинхронная отправка сообщений с гарантией доставки (At Least Once) и идемпотентностью.
- **Consumer A (SingleMessageConsumer)**: обработка сообщений по одному.
- **Consumer B (BatchMessageConsumer)**: батчевая обработка с ручным коммитом офсетов.

## Классы и принцип работы

### `MessagePayload` (в `message.py`)

Модель полезной нагрузки сообщения:
- `id`: уникальный идентификатор сообщения (инкрементируется в продюсере).
- `source`: источник (имя экземпляра продюсера, задаётся через `PRODUCER_SOURCE`).
- `payload`: полезная нагрузка (словарь).
- `metadata`: метаданные (например, timestamp).

Методы:
- `to_json()`: сериализация в JSON-строку.
- `from_json(json_str)`: десериализация из JSON-строки.

**Принцип:** единая схема сообщения для всех компонентов.

---

### Продюсер (`services/producer/service.py`)

Ключевые моменты:
- Конфигурация: `acks=all`, `enable.idempotence=True`, `retries=5` — гарантия доставки At Least Once.
- Асинхронная отправка через `produce(..., callback=delivery_report)`.
- Периодический `poll(0)` для обработки callback-ов.
- Источник (`source`) берётся из переменной окружения `PRODUCER_SOURCE`.

**Цикл работы:**
1. Генерирует `MessagePayload` с инкрементируемым `id`.
2. Сериализует в JSON.
3. Отправляет в топик.
4. Спит 1 секунду.

---

### Consumer A — SingleMessageConsumer (`services/consumer_a/service.py`)

Обрабатывает сообщения **по одному**:
- `consume(num_messages=1)` — запрашивает ровно одно сообщение.
- Обрабатывает и сразу делает коммит (`commit(asynchronous=False)`).
- Подходит для сценариев, где важна минимальная задержка и простая логика обработки.

---

### Consumer B — BatchMessageConsumer (`services/consumer_b/service.py`)

Реализует **батчевую обработку**:
- `consume(num_messages=100, timeout=2.0)` — запрашивает до 100 сообщений.
- Собирает сообщения в список `accumulated_batch` до 10 штук.
- Обрабатывает все сообщения из батча.
- Делает **один коммит** для всего батча — это повышает пропускную способность и снижает нагрузку на брокер.
- Есть gracefull shutdown для отправки накопленых сообщений если получили команду выключения 

---

## Инструкция по запуску

### Предварительные требования
- Docker и Docker Compose.
- Python 3.8+ (локально только для разработки; в контейнерах используется образ `python:3.8-slim`).

### Шаги запуска

1. **Сброс и запуск инфраструктуры (Kafka, Zookeeper, kafka-ui):**
   ```bash
   make reset
   make up-infra
   ```
2. Создание топика 
    ```bash
    make create-topic TOPIC=test-topic
    ```
3. Запуск приложения
    ```bash
    make up-apps
    ```
    При изменении работы кода:
    ```bash
    make restart-apps
    ```




## Инструкция по созданию topic.txt

### Создать топик (если ещё не создан)
make create-topic TOPIC=test-topic

### Получить описание топика и сохранить в topic.txt
docker exec "$(docker compose ps -q kafka-1)" kafka-topics \
  --bootstrap-server kafka-1:9092,kafka-2:9092,kafka-3:9092 \
  --describe \
  --topic test-topic > topic.txt.tmp


## Как проверить корректную работу приложения

Ниже — пошаговый чек‑лист проверки. Выполняй команды в отдельных терминалах (или с флагом `-d` и смотри логи отдельно).

### Шаг 1. Проверка запуска продюсера и отправки сообщений

**Команда:**
    ```bash
    docker compose logs -f producer-1
    ```
### Шаг 2. Проверка Consumer A (обработка по одному сообщению)

**Команда:**
    ```bash
    docker compose logs -f consumer_a-1
    ```
Критерий успеха:
Нет пропущенных ID (если не было сбоев), коммиты идут строго по одному, лаг (lag) в Kafka UI стремится к нулю.


### Шаг 3. Проверка Consumer B (батчевая обработка)

**Команда:**
    ```bash
    docker compose logs -f consumer_b-1
    ```
Критерий успеха:
Размер батча варьируется (зависит от fetch.min.bytes и скорости отправки), но коммит делается один раз на группу сообщений. Это подтверждает, что реализована именно батчевая стратегия.


### Шаг 4. Проверка через Kafka UI

1. Открой в браузере: `http://localhost:8080`.
2. Выбери кластер `local`.
3. Перейди в **Topics → test-topic**.

**Что проверить:**
- **Log End Offset** растёт — значит, продюсер пишет данные.
- В разделе **Consumers** найди группы:
  - `group-single` (Consumer A)
  - `group-batch` (Consumer B)
- Убедись, что у обеих групп **Lag** уменьшается или равен 0.

**Критерий успеха:**  
Обе группы читают из топика, лаг не накапливается, смещения (offsets) обновляются.

---

### Шаг 5. Проверка устойчивости к перезапускам (гарантия доставки и отсутствие дублей)

1. **Останови консьюмеров:**
   ```bash
   docker compose stop consumer_a-1 consumer_b-1
    ```
Подожди 10–20 секунд — продюсер продолжит писать сообщения.
Запусти консьюмеры снова:
    ```bash
    make up-apps
    ```
    
Посмотри логи: консьюмеры должны продолжить с последнего закоммиченного офсета и «догнать» накопленный лаг.
Дополнительно (проверка идемпотентности):
Если намеренно остановить продюсер и перезапустить, то при корректной настройке enable.idempotence=True не должно быть дубликатов сообщений с одинаковым id.

Критерий успеха:
После перезапуска лаг уменьшается до нуля, последовательность id в логах консьюмеров непрерывна (без пропусков и явных дублей).

### Шаг 6. Быстрая проверка топика через CLI 
   ```bash
    make describe-topic TOPIC=test-topic
   ```

Что смотреть:
Количество партиций: PartitionCount: 3.
Фактор репликации: ReplicationFactor: 3.
ISR (In-Sync Replicas) — все реплики должны быть в списке.
Критерий успеха:
Топик существует, все партиции имеют лидеров и синхронизированные реплики.

### Шаг 7. Проверка обработки ошибок и повторных попыток (retry & failure handling)

Этот шаг нужен, чтобы убедиться, что приложение корректно реагирует на временные сбои (например, перезапуск брокера, сетевые проблемы) и не теряет сообщения.

**Действия:**

1. **Смоделируй сбой брокера:** останови один из брокеров Kafka:
   ```bash
   docker stop kafka-2

    ```
Посмотри логи продюсера:
docker compose logs -f producer-1

Запусти брокер обратно:
docker start kafka-2


Проверь, что продюсер «догнал» очередь: в логах должны появиться подтверждения доставки (✅ Сообщение доставлено) для сообщений, отправленных во время сбоя.
Проверь консьюмеров: убедись, что они не «упали» с необработанным исключением, а продолжают читать новые сообщения и корректно обрабатывают возможные ошибки десериализации.

Критерий успеха:

Продюсер не теряет сообщения при кратковременном сбое брокера и успешно доставляет их после восстановления.
Консьюмеры продолжают работать и корректно обрабатывают ошибки (логируют, но не падают).
В Kafka UI лаг (Lag) в итоге становится 0, а последовательность id остаётся непрерывной.
